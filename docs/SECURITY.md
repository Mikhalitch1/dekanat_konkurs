# SECURITY

## Аутентификация и сессии
- Пароли: argon2id. Пароль и хэш никогда не логируются и не возвращаются в API.
- Сессии: httpOnly, Secure, SameSite=Lax cookie. Срок жизни ограничен, выход инвалидирует сессию на сервере.
- Ограничение попыток входа (rate limit по IP и логину), одинаковое сообщение об ошибке для неверного логина и пароля.
- CSRF-защита для изменяющих запросов.

## Авторизация (самое важное)
- Идентификатор текущего пользователя только из сессии. Эндпоинты вида /students/:id для студента запрещены.
- Любой запрос к заявке, оценке, расписанию или профилю фильтруется по owner = session.user. Чужой ресурс отдаёт 404, не 403.
- Роли student и staff проверяются на сервере. Staff видит только данные, нужные для обработки заявок.
- Идентификаторы: UUID, не последовательные числа.

## Данные и ввод
- Валидация zod на всех входах. Параметризованные запросы. Экранирование вывода.
- Загрузка файлов (если есть): тип, размер, хранение вне веб-корня, случайные имена.
- Только вымышленные данные.

## ИИ-помощник
- Вызов модели только с сервера. Ключ в окружении, не в коде и не в браузере.
- Модель не получает прямой доступ к БД: сервер сам собирает контекст текущего студента через ограниченные функции (расписание, оценки, заявки).
- Защита от prompt injection: пользовательский текст не может расширять права, чужие данные недоступны на уровне функций, ответы не раскрывают системный промт.
- Лимиты запросов и длины, таймауты, fallback на правила без LLM. В логи не пишутся персональные данные и содержимое диалогов.

## Транспорт и заголовки
HTTPS (Let's Encrypt через Nginx), helmet-заголовки, строгий CORS, Content-Security-Policy без inline-скриптов где возможно.

## Обязательные тесты безопасности
1. Студент A запрашивает заявку студента B по прямому ID: 404.
2. Студент пытается открыть staff-эндпоинты: 403 или 404.
3. Запрос без сессии: 401.
4. В ответах API нет password_hash.
5. В репозитории и сборке фронтенда нет ключей (grep по паттернам).
6. Rate limit входа срабатывает.
